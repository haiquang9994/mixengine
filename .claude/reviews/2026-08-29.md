## Bugs

### R17 — Two renders of one service destroyed each other's staging directory `[x]`

- [document.rs](../../crates/mixengine-core/src/generate/document.rs) staged into one fixed
  `.{service}.staging` per service and `stage` opened by deleting it. Nothing serialises two renders
  into it: `Registry::graph` renders the whole home and is reached from about fifteen places — every
  `service.*` and `site.*` handler, each `tokio::spawn`ed and joined by nobody, plus the idle
  sweeper, the certificate renewal task, the authority and `mix doctor`.
- Consequence, and it is three different failures rather than one:
  1. the second render deletes the set the first is at that moment handing to its validator, so
     `caddy validate` reports a configuration that is not there;
  2. the first comes back to commit and finds the directory it was going to rename out of gone;
  3. on Windows, where a file being read cannot be unlinked, the second render cannot delete the
     directory at all and fails with a sharing violation.
- Observed as (1) twice on `test (windows-latest)`, on two unrelated branches — the R3 work and then
  [run 33205033234](https://github.com/mixnz/mixengine/actions/runs/33205033234), whose diff
  was one test in `mixengine-proto` and two markdown files and so cannot have caused it:
  `.caddy.staging\Caddyfile: The system cannot find the file specified`. The first occurrence was
  written up in `install`'s own doc at the time and deliberately not fixed, because one occurrence
  that does not reproduce is not yet a defect somebody has understood. The second settled it.
- (3) was not predicted and turned up when the test was written — which is the argument for writing
  the test rather than reasoning about the fix.
- **Fixed** in `fix(generate): give each render a staging directory of its own (R17)`. `staging_for`
  now claims `.{service}.staging.{n}` with `tokio::fs::create_dir`, walking `n` upwards until one is
  created rather than found: directory creation is the one mutual exclusion a filesystem gives for
  free, so a render owns the name it made and no lock above it is needed to say so. `stage` no
  longer deletes anything, because the deletion existed only to clear a name somebody else might
  have left work in.
- **A lock around `Generator::declared` was the fix the first write-up proposed, and it is not this
  one.** It would serialise every RPC handler that needs the graph behind a render that can spend 30
  seconds in `caddy validate`, and it would be the only lock in the workspace held across a
  subprocess. What it buys over this is that two renders become one operation — but they read the
  same rows and commit the same bytes over each other, which is what "rendering the same state twice"
  already means everywhere else in that module, and a render whose answer differed from a concurrent
  one would be a database that changed underneath them, where the later render is the one a caller
  wanted anyway.
- The cost that is real: a crash between claiming a directory and the removal at the end of `install`
  leaves one behind, and the next render steps over it to the next number. Untidy rather than wrong —
  it is a name no service id can have, holding a rendering nobody installed — and it is written at
  `staging_for`.

## Improvements

### R18 — A yanked crate sits in `Cargo.lock` and nothing fails `[x]`

- `cargo deny check advisories` reports `warning[yanked]: detected yanked crate (try cargo update -p
  chacha20)`. It is a warning, so the `lint` job stays green.
- `chacha20` is transitive: `rand` 0.10 → `chacha20`, and `rand` is `hickory-proto`'s, for DNS
  message ids. Nothing in this workspace chose it and nothing here can choose otherwise.
- A yank is the registry's way of saying *do not build new things against this*, and the reasons
  range from a broken release to a withdrawn one to a security problem. Which of those this is has
  not been established, and that is the first thing a fix would have to do rather than assume.
- Two questions, and they are separate: whether `cargo update -p chacha20` moves off it without
  dragging `hickory` with it, and whether `yanked` should be an error in
  [deny.toml](../../deny.toml) once it is clean — the same ratchet R9 applied to duplicate versions,
  for the same reason. A warning nobody reads is not a check.
- **Fixed** in `chore(deps): move off a yanked chacha20 and fail on the next one (R18)`. Both halves:
  `cargo update -p chacha20` moves 0.10.1 → 0.10.2 and touches two lines of `Cargo.lock`, nothing
  else — `hickory` does not move, because the yanked version had a sibling inside the same
  `^0.10` — and `yanked` in `deny.toml` is now `"deny"`. Watched failing first: with the new level
  and the old lock, `cargo deny check advisories` exits 1 naming `chacha20`; with the new lock it
  exits 0.
- **The reason for the yank was established rather than assumed, and it did not need the network.**
  `chacha20`'s own `CHANGELOG.md`, 0.10.2 (2026-08-27): *"Fixed: Use of SSE4.1 intrinsic in SSE2
  backend of RNG and legacy (64-bit counter) variants"*. Both versions are still in the local
  registry cache, so it is checkable rather than merely quoted: 0.10.1's `src/backends/sse2.rs` calls
  `_mm_extract_epi32` at `:54` and `:133`, which is an **SSE4.1** intrinsic, and 0.10.2's has no
  SSE4.1 intrinsic at all.
- **So it is a crash and not a wrong answer**, which is why RustSec carries no advisory for it and
  why `cargo deny check advisories` reported only the yank. The backend is chosen by runtime CPUID —
  `cpufeatures::new!(avx512…)`, `avx2`, `sse2` — and nothing in that dispatch tests for SSE4.1. On
  x86-64, SSE2 is baseline and SSE4.1 is not, so a CPU with neither AVX2 nor SSE4.1 selects the SSE2
  backend and executes an instruction it does not have: `SIGILL`.
- Reach in this workspace: `hickory-proto` → `rand` 0.10 → `chacha20`, which is where DNS message ids
  come from. `mixengined`'s DNS server would abort on a pre-SSE4.1 x86-64 — roughly pre-2008. No CI
  runner is that old, which is exactly why nothing was ever seen and why the yank was the only
  evidence there was.
- **`yanked = "deny"` makes this build depend on somebody else's action**, which the duplicate check
  does not: a new duplicate needs a change here, a yank needs only an upstream author, so `master`
  can go red on a day nobody touched it. That is accepted rather than overlooked, and the reasoning
  is written at the setting. A yank is worth interrupting for, and the repair is one line.

### R19 — The warm-start budget sits between the two clusters it is measuring `[ ]`

- `M3`'s budget is 10000 ms and the `bench (ubuntu-latest)` distribution is bimodal: rounds land
  either around 3–6 s or around 11–19 s, with almost nothing in between. The median of five
  therefore flips on which cluster won the draw, not on the code.
- Measured during R4: the branch reported 14901 ms, then 10343, then 9071 on reruns of the same
  commit; a control run of `master` reported 5984 with one round at 18695 ms.
  [build-and-release.md](../operations/build-and-release.md)'s procedure — dispatch a `master`
  control run rather than read the diff — worked exactly as written and said "not a regression".
- The finding is not that the budget is too low. It is that a threshold placed *between* two clusters
  measures which cluster the run drew, so it fails at random on unchanged code and would pass a real
  regression that stayed inside the upper cluster. Either number would be honest; a number in the
  gap is the one that is not.
- What has not been done, and should come first: find out what the two clusters *are*. A bimodal
  start time on one runner OS is a fact about something — a cold page cache, a runner class, a
  service that sometimes waits for a lock — and a budget chosen before that is known is a guess
  whichever side of the gap it lands on.
- **Still open, and the budget is deliberately untouched. What is now known is which service it is.**
  The suite already prints the daemon's state changes for any round over the budget, and that turned
  out to be enough to split the number three ways. From `bench (ubuntu-latest)` on
  [run 33246363611](https://github.com/mixnz/mixengine/actions/runs/33246363611), three
  consecutive rounds of the same home:

  | round | caddy | **mariadb** | redis |
  | --- | --- | --- | --- |
  | 2 | 54 ms | **3411 ms** | 257 ms |
  | 3 | 54 ms | **3665 ms** | 257 ms |
  | 4 | 54 ms | **12312 ms** | 257 ms |

  The whole spread is MariaDB's `starting → running`. Caddy and Redis do not move at all.
- **How much that proves, stated carefully.** Caddy's and Redis's numbers are quantised by their own
  ready checks — Caddy polls its admin endpoint every `RETRY` = 50 ms and answers at 54, Redis spawns
  `redis-cli ping` every `COMMAND_RETRY` = 250 ms and answers at 257. Each is *one* failed attempt,
  so neither can resolve a small change in machine load. What they can show is a large one: a
  `redis-cli` spawn slow enough to matter would push Redis into the next 250 ms bucket, the way R13
  found a `cmd.exe` spawn can. Neither moved by a single bucket in the round MariaDB took twelve
  seconds. That is evidence against a general slowdown rather than proof of its absence.
- **Read as attempts, MariaDB's numbers say the server was genuinely not answering.** Against the same
  250 ms retry: a fast round is about 13–15 failed `mariadb-admin ping`s, the slow one about 49. This
  is not the harness waiting longer than it needed to; it is `mariadbd` not accepting an authenticated
  connection for twelve seconds.
- **Why it did that is not yet known, and the reason is that nobody was writing it down.** The daemon
  can only report state changes: it sees a ping fail and retry, and has nothing to say about what the
  server was doing meanwhile. `mariadbd` sends nothing to stdout — it writes `logs/mariadb.err`, the
  `log_error` this recipe renders — and that file is where a redo scan, a buffer pool being loaded or
  a start waiting on a lock would appear. The over-budget dump now includes its tail, in
  `test(bench): print MariaDB's own log when a warm round misses the budget (R19)`.
- The recipe's own comment at `StopBehaviour::Command` is the first hypothesis to check against that
  log, and it was written long before this: *"a terminated `mariadbd` leaves a dirty buffer pool, and
  the next start pays for it with a crash recovery that reads the entire redo log."* The stop before
  each slow start took about 300 ms, which is either a clean flush of very little or a shutdown that
  did not finish flushing — and `mariadb.err` distinguishes those two in one line.
- Nothing is proposed for the budget until that line has been read. Moving it to 20 s would stop the
  random reds and stop detecting anything; moving it to 6 s would make it red most runs. Both are
  worse than leaving a known-bad threshold in place for one more cycle with the evidence finally
  being collected.

- **Addendum, 2026-08-29: the commit that was supposed to collect that evidence read the wrong
  file.** `mariadb_log` —
  [warm_start.rs:455](../../crates/mixengine-cli/tests/warm_start.rs) — looked in
  `logs/mariadb.err`, and the recipe renders `log_error` into
  `logs/services/mariadb@main/mariadb.err` — every service's output goes under
  `Paths::service_logs`, and nothing about the shorter path had been checked against the template.
  Three `bench (ubuntu-latest)` rounds went over budget before it was noticed and each printed
  `(no …/logs/mariadb.err)`: three chances to read what the server said about its own slow start,
  thrown away by a diagnostic that reported its own bug as an absent log.
- The comment made it worse rather than merely failing quietly. It said a missing file *would mean
  the daemon never reached MariaDB* — a pre-written conclusion, which is exactly the reading a
  person would take from an empty dump, and which the state log in the same output contradicts.
  Fixed in `fix(test): point the M3 diagnostic at the log MariaDB actually writes (R19)`: the path is
  built from the service id the suite already declares, an absent file is reported **with a listing
  of the directory beside it** so a wrong path tells on itself, and the sentence interpreting absence
  is gone. **R19 itself stays open** — the budget is still in the gap and the log has still not
  been read.

### R20 — The daemon's log rotation fails on Windows, says so, and fails nothing `[ ]`

- On `test (windows-latest)` in
  [run 33186251226](https://github.com/mixnz/mixengine/actions/runs/33186251226):
  `ERROR mixengined::logging: log rotation failed; this file will keep growing error=Access is
  denied. (os error 5)`. One occurrence. **It is not why that run was red** — that was the
  `packages.rs` `ERROR_PIPE_BUSY`, and this line merely shares the log with it.
- **Most of the design already anticipates this.**
  [rotating.rs:106](../../crates/mixengine-supervisor/src/logs/rotating.rs) —
  `RotatingFile::rotate` — drops its own handle before
  the rename because Windows refuses one this process holds, backs off by a whole `max_bytes` rather
  than retrying per line, and complains in the log's own format so a collector parsing JSON is not
  handed a plain sentence. A rename that a backup agent or an antivirus is holding open is the case
  it is written for, and a hosted runner with Defender on it is where that case lives. So this may
  be precisely the accepted outcome, working.
- **What is not explained is the part worth keeping.** That file's comment says closing the handle
  first is what makes the rename allowed — *"with the two lines the other way round, three of the
  tests below fail on Windows with 'access denied' and none of them on Linux or macOS"*. Here the
  handle was closed and the rename was still refused, so something outside this process held it.
  Who is not established: Defender is the likely answer, a test harness reading `daemon.log` is
  another candidate, and neither was checked. Nothing should be changed until one of them is.
- **The second observation is the more surprising one, and the first nearly hides it.** Rotation
  fires only at `MAX_BYTES` —
  [logging/mod.rs:37](../../crates/mixengine-daemon/src/logging/mod.rs) — a fixed 10 MB with no
  override — so `daemon.log` reached ten
  megabytes inside a single test job. Whether that is ordinary for a debug-level daemon under a
  suite or a sign that something logs far more than it should has not been measured; but a daemon
  producing 10 MB in one job produces a great deal more in a day of real use, and the answer changes
  what `KEEP = 5` is worth keeping.
- **How this was nearly recorded wrongly.** It was carried between sessions as a note reading *"the
  Windows install-rename `Access is denied`, one occurrence, 450 ms retry budget at
  `RENAME_ATTEMPTS`"* — a different subsystem, a different file, and a retry budget with nothing
  to do with it. Reading the log again is what corrected it. A finding kept as a sentence rather than
  as a run id and a quoted line drifts, and the drift is invisible because the sentence still sounds
  specific.

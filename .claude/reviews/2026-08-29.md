## Bugs

### R17 — Two renders of one service destroyed each other's staging directory `[x]`

- [document.rs](../../crates/mixengine-core/src/generate/document.rs) staged into one fixed
  `.{service}.staging` per service and `stage` opened by deleting it. Nothing serialises two renders
  into it: `Registry::graph` renders the whole home and is reached from about fifteen places — every
  `service.*` and `site.*` handler, each `tokio::spawn`ed and joined by nobody, plus the idle
  sweeper, the certificate renewal task, the authority and `mix doctor`.
- Consequence, and it is three different failures rather than one:
  1. the second render deletes the set the first is at that moment handing to its validator, so
     `caddy validate` reports a configuration that is not there;
  2. the first comes back to commit and finds the directory it was going to rename out of gone;
  3. on Windows, where a file being read cannot be unlinked, the second render cannot delete the
     directory at all and fails with a sharing violation.
- Observed as (1) twice on `test (windows-latest)`, on two unrelated branches — the R3 work and then
  [run 33205033234](https://github.com/haiquang9994/mixengine/actions/runs/33205033234), whose diff
  was one test in `mixengine-proto` and two markdown files and so cannot have caused it:
  `.caddy.staging\Caddyfile: The system cannot find the file specified`. The first occurrence was
  written up in `install`'s own doc at the time and deliberately not fixed, because one occurrence
  that does not reproduce is not yet a defect somebody has understood. The second settled it.
- (3) was not predicted and turned up when the test was written — which is the argument for writing
  the test rather than reasoning about the fix.
- **Fixed** in `fix(generate): give each render a staging directory of its own (R17)`. `staging_for`
  now claims `.{service}.staging.{n}` with `tokio::fs::create_dir`, walking `n` upwards until one is
  created rather than found: directory creation is the one mutual exclusion a filesystem gives for
  free, so a render owns the name it made and no lock above it is needed to say so. `stage` no
  longer deletes anything, because the deletion existed only to clear a name somebody else might
  have left work in.
- **A lock around `Generator::declared` was the fix the first write-up proposed, and it is not this
  one.** It would serialise every RPC handler that needs the graph behind a render that can spend 30
  seconds in `caddy validate`, and it would be the only lock in the workspace held across a
  subprocess. What it buys over this is that two renders become one operation — but they read the
  same rows and commit the same bytes over each other, which is what "rendering the same state twice"
  already means everywhere else in that module, and a render whose answer differed from a concurrent
  one would be a database that changed underneath them, where the later render is the one a caller
  wanted anyway.
- The cost that is real: a crash between claiming a directory and the removal at the end of `install`
  leaves one behind, and the next render steps over it to the next number. Untidy rather than wrong —
  it is a name no service id can have, holding a rendering nobody installed — and it is written at
  `staging_for`.

## Improvements

### R18 — A yanked crate sits in `Cargo.lock` and nothing fails `[ ]`

- `cargo deny check advisories` reports `warning[yanked]: detected yanked crate (try cargo update -p
  chacha20)`. It is a warning, so the `lint` job stays green.
- `chacha20` is transitive: `rand` 0.10 → `chacha20`, and `rand` is `hickory-proto`'s, for DNS
  message ids. Nothing in this workspace chose it and nothing here can choose otherwise.
- A yank is the registry's way of saying *do not build new things against this*, and the reasons
  range from a broken release to a withdrawn one to a security problem. Which of those this is has
  not been established, and that is the first thing a fix would have to do rather than assume.
- Two questions, and they are separate: whether `cargo update -p chacha20` moves off it without
  dragging `hickory` with it, and whether `yanked` should be an error in
  [deny.toml](../../deny.toml) once it is clean — the same ratchet R9 applied to duplicate versions,
  for the same reason. A warning nobody reads is not a check.

### R19 — The warm-start budget sits between the two clusters it is measuring `[ ]`

- `M3`'s budget is 10000 ms and the `bench (ubuntu-latest)` distribution is bimodal: rounds land
  either around 3–6 s or around 11–19 s, with almost nothing in between. The median of five
  therefore flips on which cluster won the draw, not on the code.
- Measured during R4: the branch reported 14901 ms, then 10343, then 9071 on reruns of the same
  commit; a control run of `master` reported 5984 with one round at 18695 ms.
  [build-and-release.md](../operations/build-and-release.md)'s procedure — dispatch a `master`
  control run rather than read the diff — worked exactly as written and said "not a regression".
- The finding is not that the budget is too low. It is that a threshold placed *between* two clusters
  measures which cluster the run drew, so it fails at random on unchanged code and would pass a real
  regression that stayed inside the upper cluster. Either number would be honest; a number in the
  gap is the one that is not.
- What has not been done, and should come first: find out what the two clusters *are*. A bimodal
  start time on one runner OS is a fact about something — a cold page cache, a runner class, a
  service that sometimes waits for a lock — and a budget chosen before that is known is a guess
  whichever side of the gap it lands on.

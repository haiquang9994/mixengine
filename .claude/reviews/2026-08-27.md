# Review 2026-08-27 — the whole workspace at `d29e6dc`

**Scope.** 9 crates, 135,808 lines of `.rs` (99,244 code, 36,564 comment, 26,016 integration
test), 129 commits since 2026-08-10, a 1,230-line `.github/workflows/ci.yml`, ~115k words under
`.claude/`. `cargo check --workspace --all-targets` is clean. Nothing was changed by this review.

**Method.** Four independent passes — security (IPC, elevate, download chain, secrets, DNS, panics),
tests/CI (gates, `#[ignore]`, coverage, flakiness), docs-vs-code (RPC surface, roadmap, spec
contradictions), code quality (large files, `cfg`, `anyhow`, async, dependencies) — then every
`file:line` cross-checked.

**One-line verdict.** Unusually high discipline: no `TODO`, no `unwrap()` outside tests in
core/daemon, no `unsafe` outside `mixengine-platform`, layering enforced by a test, roadmap matching
the code at 59/59 RPC methods. The real weaknesses are **one pipe-identity hole on Windows**, **CI
that can be green for the wrong reason**, and **the maintenance cost of the comment density**.

## Bugs

### R1 — The client never verifies who is serving the named pipe (Windows) `[x]`

- [windows/ipc.rs:188](../../crates/mixengine-platform/src/windows/ipc.rs#L188) `connect()` opens
  `\\.\pipe\mixengine.<sid>.<fnv(run)>` and checks nothing about the serving side. The name is
  predictable (`fingerprint()` is FNV-1a; the comment at `:81-91` itself says "a name, not a
  defence"); the Win32 pipe namespace is flat and any account can create in it.
- Consequence: another account on the same machine creates the pipe before the daemon comes up and
  receives everything `mix` sends (every request, `elevation.*` included).
- The daemon half is right: `FILE_FLAG_FIRST_PIPE_INSTANCE` (`:107`, `:257`) makes `bind` *refuse*
  a taken name; DACL `D:P(A;;GA;;;<owner>)` (`:418`); `reject_remote_clients` (`:280`); peer check
  by impersonation (`:334-375`). Only the reverse direction is missing.
- Unix is not exposed: the socket sits in a `run/` already locked down by `DirectoryAccess`, plus
  `0600` ([unix/ipc.rs:112](../../crates/mixengine-platform/src/unix/ipc.rs#L112)).
- Fix: after `CreateFile`, `GetNamedPipeServerProcessId` → open the process → compare its owner SID
  with our own; on mismatch close and return a named error. A private namespace
  (`CreatePrivateNamespace`) is the heavier alternative and not needed for a single-user model.
- This sits inside the "trusted single-user machine" model that
  [security-model.md](../architecture/security-model.md) assumes, but it is the one place where
  that assumption is load-bearing and unstated.
- **Fixed in #41.** `connect` now reads the **owner of the pipe object** and hangs up before the
  first byte on one this account does not own, with `Error::EndpointNotOurs` naming who answered.
  Not the pid
  the fix above suggested: `GetNamedPipeServerProcessId` hands back a number the OS may have reused
  by the time it is turned back into a process, which is the very objection `peer_of` states for the
  other direction — while an owner is stamped on at creation and cannot be set to an account the
  creator does not hold. That made a second change necessary: the pipe's descriptor now *states*
  `O:<sid>` instead of letting the creating token supply a default owner, which is a machine policy
  ("Default owner for objects created by members of the Administrators group") and not a fact.
  `bind`'s probe was widened to the same question, because it is the message a squat surfaces
  through *first*: it already dialled the name to tell "taken" from "refused", and answering "another
  process is already listening" sends the user hunting for a daemon of their own to stop while a
  stranger holds the name. It now says who, through the same `EndpointNotOurs`.
  Autostart needed nothing — `is_absent` in the CLI already excluded everything but
  `NotFound`/`ConnectionRefused`, so the new error is reported rather than answered by starting a
  second daemon. Both error mappers did: the variant fell through to `internal` in each, which tells
  the person holding the one message that says another account is on their endpoint to go and file a
  bug. Both now answer `conflict`, and neither hint offers `mix daemon stop` — there is no daemon of
  theirs to stop.
  Seven unit tests in `windows/ipc.rs` and one in each mapper: the descriptor names an owner (this
  one fails without the `O:`), the pipe a `Listener` creates is owned by this account, dialling it as
  its owner works, dialling it as somebody else is refused, and the three answers `bind`'s own probe
  can give are told apart. The account boundary itself is what none of them cross — Windows will not
  let a standard process claim another account's SID as an owner, so what the refusal tests vary is
  the *expectation*, everything else being a real pipe and a real read off it. The genuine
  cross-account case needs a second account and belongs to the `system` job, which R3 shows does not
  run yet.
  The assumption is now written down, in [security-model.md](../architecture/security-model.md) and
  in [daemon-and-ipc.md](../architecture/daemon-and-ipc.md).

### R2 — The `connections` suite says it "runs in the system job", and the job never calls it `[x]`

- [connections.rs:26](../../crates/mixengine-platform/tests/connections.rs#L26):
  `#[ignore = "opens a real socket; runs in the system job"]`.
- `grep -- '--test connections' .github/workflows/ci.yml` → nothing. The `system` job
  (`ci.yml:845`) names each suite explicitly; this one is not in the list.
- Fix: add it to all three legs, or correct the ignore reason.
- **Fixed in #42**, by adding the step rather than by correcting the reason: a suite that measures
  the one thing about this capability no unit test can reach is worth a runner. **The `test` job and
  not `system`**, though, which is what the suite claimed for as long as nothing ran it. Counting
  connections needs no administrative token, and `system` is the job for what an unprivileged
  process cannot prove — what this needs is a real socket on each of the three mechanisms, and
  `test` is the job with a leg on each. It is `#[ignore]`d and given a step of its
  own in the `certutil` step's shape rather than being let into the workspace run, so a leg where it
  did not run says so instead of reporting a pass. On Linux it sits outside the network namespace,
  deliberately: inside it the tables hold this test's own sockets and nothing else, while picking one
  port out of the machine's whole table is the harder question and the one the idle sweeper asks.
- **The first real measurement is green on all three** — run 33169664473, one test run and passed on
  each of `windows-latest`, `ubuntu-latest` and `macos-latest`. Measured on this machine and in WSL
  before it was pushed, so the round trip was asked for macOS's answer, which is the one nothing here
  can give.
- **One thing macOS's green leaves open**, and it is not this finding's to close: `lsof -iTCP:<port>`
  matches the port at *either* end, so both sockets of a loopback connection are files it can see —
  yet `-t` answered with one line. Either the address filter matched only the local end, or `-t`
  prints one line per *process* and not per file, which would make `established_on` a count of
  processes and the note at
  [macos/ports.rs:49](../../crates/mixengine-platform/src/macos/ports.rs#L49) ("Two clients from one
  process are two lines") wrong. **Nothing in the build can tell today**: the sole consumer,
  [idle.rs:85](../../crates/mixengine-supervisor/src/idle.rs#L85), maps `Ok(0)` to `Idle` and every
  other count to `Busy`, so the two readings are the same answer. Worth a finding of its own the day
  a caller wants the number itself.
- **The audit this finding invites came back with one name.** Every other `#[ignore]`d suite no
  `--test` line mentions is either conditional on `not(debug_assertions)` — the `fakeservice` ones,
  which do run, in the debug build CI uses — or is R3's and `index.rs`'s. `connections` was the only
  suite claiming a job that never called it.

### R3 — `MIXENGINE_SYSTEM_TESTS=1` is mentioned in four places and set in none `[x]`

- [cert.rs:428](../../crates/mixengine-cli/tests/cert.rs#L428) and
  [caddy.rs:303](../../crates/mixengine-cli/tests/caddy.rs#L303) are double-gated: `#[ignore]`
  **and** `std::env::var("MIXENGINE_SYSTEM_TESTS") == "1"`. No file under `.github/` exports the
  variable.
- Consequence: **CA rotation and trust-store writes have never run in CI**, although T52–T54 are
  ticked `[x]`.
- Fix: export it in the `system` job (that is the job designed to write to the machine) and add
  the two suites to its list.
- **Fixed in #43.** The `system` job sets the variable and runs both suites, but **not on the
  same three legs**, which is where this diverges from the fix above. The `cert` invariant runs
  everywhere; the end-to-end `caddy` rotation runs on Windows and macOS only.
  It asserts `outcome == "rotated"`, so it needs a grant — and a Linux runner has no polkit agent,
  which is not a gap in the job but ADR 0005's worst branch, asserted for real by the launcher suite
  beside it. On Linux the rotation is refused whoever asks, root included, so that test could only
  ever fail there; what Linux answers is the refusal, and that is exactly what `cert` asserts. macOS
  earns its leg from a measurement already in this job: the launcher step established that `do shell
  script … with administrator privileges` on a process that is already root runs straight through,
  so the suite runs under `sudo` and the rotation is granted. The job also had to learn to build the
  CLI, the daemon and the helper into one directory, fetch a real Caddy, and it went from 20 minutes
  to 35 with clocks of its own on the steps that could hang rather than fail.
- **The first run of it found a bug three tasks had been carrying, and that is the whole argument for
  this finding.** T51 renders a certificate fingerprint into the generated site file so that a
  reissue produces bytes that *differ* — which is what makes `document::install` notice and ask the
  front end to re-read. That half works. The other half does not: `caddy reload` adapts the Caddyfile
  to JSON and **the adapter throws comments away**, so the configuration Caddy is handed after a
  reissue is identical to the one it is running, its admin endpoint skips the load, and the process
  goes on presenting the certificate it holds in memory. Both legs found precisely that — a rotation
  reporting success, the leaf on disk signed by the new authority, the handshake presenting one
  signed by the old, `problem: served_certificate_differs`, `trust: rejected`. The line that exists
  to trigger the reload is the one line the server never sees. `recipes::caddy` passes `--force` now,
  which `caddy reload --help` on the pinned 2.11.4 documents as *force config reload, even if it is
  the same* — measured against the binary rather than read about. **T52's renewal reissues on the
  same path**, so a renewed certificate was never served either; nothing had ever reissued against a
  running Caddy and read the handshake back.
- **Two things this left behind rather than closed.** `ca-rotate` reports success when the front end
  has been *told*: the registry writes the rendering and notifies, the service's own task reloads. So
  the acceptance criterion is bounded rather than instant, and the test polls for it — which is what
  "afterwards" means and not a softening of it, but it does mean `mix cert status` run in that window
  answers `served_certificate_differs` about a rotation that worked. And
  [document.rs:308](../../crates/mixengine-core/src/generate/document.rs#L308) stages every install
  into **one fixed directory per service** (`.caddy.staging`), which `stage` opens by deleting and
  recreating, with no lock anywhere in [generate.rs](../../crates/mixengine-core/src/generate.rs)
  around `declared`. Two renders of one service that overlap therefore corrupt each other, and the
  symptom is exactly the one a Windows leg produced once on this branch: `stage` reports success and
  the validator is then handed a directory with no entry file in it. It did not reproduce on a rerun
  and is not fixed here; the defect is provable from the code whether or not that run is what it was.

### R4 — `test-no-network.sh` downgrades a missing package to `::warning`; the job stays green `[x]`

- [test-no-network.sh:143](../../.github/scripts/test-no-network.sh#L143), `:152`, `:160`, `:191`,
  `:201`, `:211`, `:219`, `:225` — when `MIXENGINE_<X>_PACKAGE` is unset, that recipe's real-server
  suite is skipped with a warning.
- Consequence: a broken package fetch (mirror down, index rotated, checksum mismatch) removes every
  Caddy/nginx/MariaDB/MySQL/PostgreSQL/Redis/Memcached test from the Linux leg and the result is
  still ✅.
- Fix: `exit 1` with the same message. If a developer machine without packages needs an escape
  hatch, gate it behind its own variable (`MIXENGINE_ALLOW_MISSING_PACKAGES=1`), not the default.
- **Fixed in #44**, with the escape hatch this asked for: ten `::warning` branches now call one
  `missing` helper that prints `::error` and exits 1, and only warns when
  `MIXENGINE_ALLOW_MISSING_PACKAGES=1` is set — a variable somebody has to type, which is the
  difference between an exception and a default. It is written down in
  [build-and-release.md](../operations/build-and-release.md) beside the other knobs, and nothing in
  CI sets it.
- **The consequence as stated does not hold today, and saying so is part of the record.** A mirror
  that is down does not reach these branches at all: every fetch step runs `set -euo pipefail` with
  `curl --fail --retry 3`, so a failed download fails *that step* and the job stops before this
  script is reached — and `Linux-X64`, the only architecture this leg runs on, has a published
  archive for all nine packages. The warning branches were unreachable on CI rather than quietly
  firing. What the change buys is therefore not a hole closed but a contract enforced by the thing
  that holds it, for two live cases: a fetch step that learns to skip on Linux — **three of them
  already do exactly that on Windows-ARM**, `::notice` and `exit 0` — and a developer running the
  script by hand, which is who the warning was really written for.
- **One thing of the same shape is deliberately left alone.** `ci.yml`'s nginx step carries
  `if: … && env.MIXENGINE_NGINX_PACKAGE != ''`, which is a step that removes itself when a variable
  is empty — this finding's shape, in the workflow rather than in the script. It has a reason
  written beside it and it serves a Windows-on-ARM leg that does not exist yet, where no upstream
  publishes an nginx; taking the guard away would break that leg on the day it is added, to close a
  path nothing walks. The day an ARM leg lands is the day to decide whether a leg that cannot run a
  suite should say so as a skip or as a smaller matrix.
- A stale comment beside the change went with it: "the one `#[ignore]`d suite this job runs" had
  nine more below it.

### R5 — `std::fs::remove_dir_all` inside an `async fn` `[x]`

- [elevation.rs:595](../../crates/mixengine-daemon/src/elevation.rs#L595), inside `flush()`
  starting at `:535`. The **only** place in daemon+core that does synchronous I/O on a tokio
  worker; everything else goes through a documented `spawn_blocking` (`api/logs.rs:159`,
  `rpc.rs:662`, `certs.rs:384/420/666`, `runner.rs:1621/1760/2009`, …).
- Low impact (a small request directory, best-effort), but it is the one exception to a rule the
  rest keeps absolutely.
- Fix: `tokio::fs::remove_dir_all(...).await`.
- **Fixed on `fix/r5-no-blocking-io-on-a-worker`**, as written, and through `tokio::fs` rather than
  the explicit `spawn_blocking` the certificate and log paths use: there is one call to move, and
  `tokio::fs` *is* that hand-off, without a closure for the next reader to look past.
- **"The only place" was checked rather than taken.** Fixing one instance of an invariant and
  leaving its siblings is the failure this workspace's own working agreements name, so the sweep was
  run: `diagnostics.rs` holds six synchronous calls and every one of them is inside `pack`, a
  non-async fn reached through the `spawn_blocking` at
  [diagnostics.rs:163](../../crates/mixengine-daemon/src/diagnostics.rs#L163); every `std::fs` in
  `mixengine-core` sits in a synchronous function — `ca::discard`, `leaf::read`, `config::read`,
  `elevation::write_request` — because core is a synchronous library and the daemon is where the
  hand-off lives; the rest is `#[cfg(test)]`. The finding was right, and now it is known to be.
- **No test distinguishes this change, and inventing one would be theatre.** It alters *how* and not
  *what*: the assertion that the single-use directory is gone after a grant
  ([elevation.rs:1033](../../crates/mixengine-daemon/src/elevation.rs#L1033)) passes before and
  after, which is exactly what a change of this kind must leave true.

## Done well

What to preserve when refactoring. No checkboxes — these are invariants, not work.

- **Real IPC peer authentication on both platforms.** Unix compares `SO_PEERCRED`/`LOCAL_PEERCRED`
  on every accept ([unix/ipc.rs:136-152](../../crates/mixengine-platform/src/unix/ipc.rs#L136-L152)),
  does not special-case root, and says why. Windows uses *impersonation* rather than
  `GetNamedPipeClientProcessId` — the only pid-free way to ask — holds it across two synchronous
  calls with nothing awaited, and `abort()`s the process if `RevertToSelf` fails
  ([windows/ipc.rs:369-372](../../crates/mixengine-platform/src/windows/ipc.rs#L369-L372)) rather
  than returning a tokio worker to the pool wearing a stranger's token. Rarely done right.
- **`mixengine-elevate` genuinely distrusts its caller.** The request is a file, not argv or a pipe.
  [request.rs](../../crates/mixengine-elevate/src/request.rs) checks, in order: symlink refused
  before any read (`:48`), caller identity taken from the *filesystem* rather than the document
  (`:56`), superuser-owned (`:61`) and world-writable (`:68`) files refused, an existing response
  file as stateless anti-replay (`:80`), home owned by the caller (`:114`), request inside the home
  (`:125`). The TOCTOU between the metadata checks and `read_to_string` (`:87`) is not exploitable,
  because every security-relevant field is re-derived from the *parsed* document. There is no
  `Exec` variant; hosts writes accept only `127.0.0.1`/`::1` (even `127.0.0.2` is rejected),
  domains in `MANAGED_TLDS`, capped at 512 lines. The audit log is root-owned and **outside**
  `MIXENGINE_HOME`, with the rename/unlink reasoning at
  [audit.rs:1-20](../../crates/mixengine-elevate/src/audit.rs#L1-L20). The macOS `osascript` takes a
  compile-time-constant script with paths passed as `argv`.
- **The supply-chain order is correct.** The signature is verified *before* the JSON is parsed
  ([index.rs:308-326](../../crates/mixengine-core/src/index.rs#L308-L326)), the legacy minisign
  algorithm refused; rollback blocked on `generated_at` (`:245-256`); SHA-256 checked before unpack
  (`install.rs:239` → `:247`), a mismatch deletes the download; path traversal blocked twice — a
  component scan ([archive.rs:111](../../crates/mixengine-core/src/install/archive.rs#L111)) and
  then `enclosed_name`/`unpack_in` (`:134`, `:193`); `set_unpack_xattrs(false)`. `minisign-verify`
  in the binary, `minisign` (the signing half) only in testkit; `ruzstd` reads, the C `zstd` only in
  testkit — what the product reads is proved against what a *different implementation* wrote.
- **Secrets never touch argv, generated config, or logs.** Passwords are late-resolved
  `EnvValue::Keyring` references
  ([recipes/mariadb.rs:751-753](../../crates/mixengine-core/src/generate/recipes/mariadb.rs#L751-L753));
  MySQL uses a narrowly permissioned, always-removed `SecretFile` with a redacting `Debug`
  ([first_run.rs:133](../../crates/mixengine-daemon/src/services/first_run.rs#L133)); Postgres goes
  through stdin. A test asserts the invariant (`recipes/mysql.rs:804-805`).
- **DNS is loopback-only**, `recursion_available = false`
  ([dns/server.rs:70](../../crates/mixengine-daemon/src/dns/server.rs#L70), `:121`) — no
  amplification path off the machine. `hickory-server` with no default features, no resolver, no
  second SQLite.
- **A panic is a value, not a dead daemon.** Every RPC runs in its own task
  ([rpc.rs:165-180](../../crates/mixengine-daemon/src/api/rpc.rs#L165-L180)); `panic = "abort"` is
  explicitly forbidden in `Cargo.toml` with the reason; the `daemon.__panic` handler is gated
  behind `#[cfg(test)]`.
- **Near-perfect async hygiene.** No `block_on`, `blocking_lock`, `thread::sleep`, or blocking sqlx
  anywhere in daemon+core; every synchronous I/O is wrapped in a documented `spawn_blocking`. The
  single exception is R5.
- **End-to-end tests against real things, not mocks.** A real daemon spawned from
